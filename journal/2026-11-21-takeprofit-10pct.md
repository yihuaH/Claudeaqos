# 2026-11-21 止盈档 +20% → +10% (用户指令)

用户原话:「每个都设个10%止盈」。

## 改了什么

`strategy/qqq_leap.json` → `exit.take_profit_mult`: **1.2 → 1.1**。只改这一个数,
判定口径 (`bid ≥ 入场 ask 成交价 × mult`) 与判定频率 (每交易日收盘前窗口一次) **都不变**。

## 📐 为什么一个数就等于「每个都设」

`qqq_leap.py:363` 判定出场时是**实时重算**的:
```python
tp_line = round(float(pos["entry_fill_price"]) * float(ex["take_profit_mult"]), 4)
```
它**不读**账本里存的 `take_profit_line` —— 那个字段只是开仓那一刻的快照。
所以改 config 当场对**全部五张在手仓生效**, 不需要改账本 (也不该改, 红线: 会话不得手工改仓位数据)。

## 🔴 顺带查出并修掉一个报告级缺陷: `tp_reachability.py` 读的是账本快照

改完 config 后第一次跑可达性工具, 输出的止盈线**还是旧值** —— 查出
`tp_reachability.py:192` 原本是 `tp = float(pos["take_profit_line"])`, 即**读账本快照**,
与引擎的「按 config 实时重算」是两套口径。

⚠️ **之前两者一直相等纯属巧合** (快照正是用同一个 mult 写的), 所以这个错从工具 11-17 建起
到今天一直没显形。**改 mult 的这一刻它就显形了**: 若不修, 从周一起战报上印的止盈线
会与引擎真正判定的线差一整档 —— 而这个工具存在的唯一目的就是回答「还差多少」, 读错线
就是直接误导用户。

🔧 已改为复用引擎的算式 `entry_fill_price × cfg["exit"]["take_profit_mult"]`, 并在原处写明理由。
✅ **双向验证**: 用新 config (1.1) 跑出新线 19.096 / 15.312 / 18.931 / 17.325 / 13.431;
把 mult 临时改回 1.2 再跑, **逐字重现今日战报里的旧值** (20.832 / 16.704 / 20.652 / 18.900 / 14.652)。

## ⚠️ 必须记下的两件事

1. **+10% 不在回测覆盖范围内**。§18.1 的扫描最低一档是 **+15%** (六档 +15/20/25/30/35/50)。
   可外推的是 §18.4 的实测结论「有 20 日时间止损之后止盈档对 alpha 几乎无关」
   (六档信号增量 +11.50~+12.55pp 无趋势, p10 全 −43.6%、最差全 −69.3% 由时间止损决定),
   故降一档**大概率不改变 edge**, 改变的是形状: 按 +15%→+20% 的方向外推, +10% 预期
   胜率更高、持有更短、占资更低、**单笔均值更低** (+15% 档 +14.20% vs +20% 档 +15.13%)。
   **外推一档终究是外推**, 要确数需给 §18 扫描补一个 +10% 档。
2. **点差占目标的比例变大**。判定口径已净扣双边点差, 故 +10% 是真实净收益; 但目标越小,
   往返点差占比越高 —— 本轨道实测 1.9%~4.7%, **330 档可达 10%**, 那一档的 +10% 目标
   实际要求权利金涨到 +20% 以上才够。§14 在 QQQM 上已见过这个失效模式。
